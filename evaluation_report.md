evaluating this model / experiment, at honours scope (defensible rigour, not
journal-grade). Derived only from the repo: code, configs, results CSVs,
summary.json files, plots, slides, proposal, scoped-RQ doc, research log,
takeoff/status.md, and defence/. The transcription folder was not read.

Tags: [BUG] something is wrong in code/artifacts. [GAP] promised but missing.

## 2. The claim that cannot be dodged: buy-and-hold

- [DO] Report prominently that neither mechanism beats the buy-and-hold floor: mean B&H Sharpe 0.841 vs FS 0.387 and AS 0.465 across all 868 rows; the agent beats B&H in only 27.2% (FS) and 24.5% (AS) of the 217 (seed, window) pairs per mechanism. Reason: the proposal itself set this rule ("no configuration that fails to beat buy-and-hold earns a 'useful trader' label"), so the project is graded against its own stated criterion.
- [DO] State explicitly that this does not invalidate RQ2. Reason: RQ2 is a *relative* mechanism comparison (AS vs FS at matched k), which remains meaningful even when both are below a passive benchmark — but the report must say this rather than letting the reader assume the agents are profitable.
- [GAP] No constant-long control separate from B&H, and no random-policy or untrained-policy control. Reason: the agents are long on ~70-78% of test days (FS k=3: 191 long / 43 short / 18 flat out of 252), so most of the measured Sharpe is market beta in a mostly-rising sample, not skill. A random-position and a frozen-init-policy control cost one rollout each and separate "learned something" from "happened to be long".
- [DO] Add a transaction-cost sensitivity curve (recompute rewards from steps.csv at 1, 5, 10, 25 bps). Reason: the configs use 0.0001 (1 bp) per unit of position change, which is optimistic; agents flip positions often, so the ranking may be cost-dependent. This is a standard robustness check and costs no retraining.

## 3. Design-vs-motivation inconsistencies (highest-value fixes)

- [BUG] The agent never observes the VIX *level* — it observes the VIX *log-return* (transforms.py:31, fed to TimeSeries as `observations`). Reason: the entire motivation in the proposal and Week 2 slides is that the VIX level encodes regime and that "a spike from six weeks back still shapes today's level". Log-differencing removes exactly that persistence, so the sparse-informative-observation premise that Adaptive Stacking depends on is destroyed before the agent sees anything. Either (a) feed the level (z-scored on the train slice) or a level-plus-change pair, or (b) state plainly in the report that the observation is a differenced series and that this weakens the sparsity premise. (a) is one line of code and is the single most defensible experimental improvement available.
- [BUG] The agent's own current position is not in the observation (timeseries_env.py:29, `_obs` returns only the observation value), yet the reward depends on it through the transaction cost (timeseries_env.py:60-63). Reason: this makes the env non-Markov in a way that was not intended and that no memory mechanism can fix — the agent cannot know whether an action incurs a cost. Standard practice in financial RL (Moody & Saffell onward) includes the current position in the state. Fix it, or document it as a known limitation that penalises all three configurations equally.
- [GAP] Slides and proposal describe four configurations and three RQs; `scopedinrqs.md` drops the memoryless PPO (k=1) baseline and RQ2-original. Reason: the deck and the proposal are now inconsistent with what was run, and the scope cut must appear in the report with its reason, or a marker will read the gap as an omission. Also: with no k=1 run, the claim "memory helps on financial data" cannot be made at all — only "learned memory vs fixed memory".
- [DO] A k=1 PPO run is cheap (31 windows x 7 seeds at the same 100k timesteps) and restores the dropped step of the staircase. Reason: it also gives the only clean answer to "is any of this better than reacting to today's VIX alone", which is the first question any examiner asks.
- [OK] Matched-budget design is genuinely honest: identical PPO block, identical walk-forward, identical k grid, identical cold-start fill, flattened observation of the same shape (adaptive_stack.py:40-53, 94-105). Reason: this is the part of the methodology that is strongest — say so explicitly and point at the two configs side by side.
- [STAT] AS is not parameter-matched or action-space-matched to FS: it carries an extra memory head and a MultiDiscrete([3, k]) action space at the same 100k timesteps. Reason: AS has a harder learning problem at equal compute, so a null result is partly confounded with sample budget. Either note it as a limitation or add one AS run at a larger timestep budget to show the result is not budget-limited.

## 4. Evaluation protocol / leakage

- [BUG] Model selection happens on the test data. `compute_champion` ranks k (and LSTM hp_id) by mean Sharpe over the walk-forward *test* windows (train.py:174-197; train_lstm.py:174-199), and the same windows are then used to report the result. Reason: this is in-sample selection — the reported champion Sharpe is biased upward, and the bias grows with the number of configurations tried (4 k values x 2 mechanisms x 4 LSTM shapes = 10 selections against one test set). Bailey & Lopez de Prado's deflated-Sharpe argument is exactly this: a hold-out does not remove data-snooping bias when many strategies are tested against the same hold-out.
- [DO] Minimum credible fix at honours scope: carve a validation slice inside each training window (e.g. last 252 train days), select k / hp there, and report the selected config once on the test windows. Reason: no retraining of the sweep is needed if you instead do the cheaper version — report *all* k values rather than a champion, and label any "best k" as selected in-sample.
- [GAP] The final-holdout rule the project set for itself (last ~2 years untouched) was never enforced; all sweeps use the full 1990-2026 range. `takeoff/status.md` already admits this. Reason: it has to be either implemented or written up as a deviation with the reason, because the design_doc explicitly draws it as a "hard rule" line.
- [BUG] No gap/embargo between train and test slices. Walk-forward windows are contiguous (walk_forward.py:69-92) and the target is a shifted next-day return (transforms.py:39), so the last training day's label covers the first test day's price move. Reason: a one-day leak is small but free to remove — drop one row at each boundary (purged/embargoed walk-forward, Lopez de Prado). Worth a footnote either way.
- [STAT] The 31 windows are not independent: train_size 1260 with step 252 means adjacent windows share 4/5 of their training data. Reason: any error bar or test that treats windows as i.i.d. overstates confidence; say so, and prefer a block bootstrap over windows.
- [OK] Per-window z-scoring for the LSTM is fit on the train slice only (lstm.py:81-94, train_lstm.py:296-303). Reason: correct and worth stating, since it is the obvious place a leak would hide.
- [BUG] The RL side applies no observation normalisation at all (no VecNormalize, raw log-returns with std 0.068 into an MLP). Reason: this is an unequal-footing difference between the LSTM baseline and the PPO agents, not just a tuning choice; mention it, or add VecNormalize to both arms.
- [DO] Report a train-slice vs test-slice Sharpe gap per config. Reason: each PPO agent sees one 1260-day trajectory for 100k timesteps (~79 passes over the same data) with no early stopping, so overfitting is the default expectation and the gap is the only evidence either way.

## 5. Statistics and inference

- [STAT] Error bars in the current plots are std over seeds x windows pooled (generate_plots.py:238-293: "mean Sharpe ± std across seeds × windows"). Reason: this pools two different variance sources (which environment year it was, and which random seed) and treats 217 rows as 217 independent samples — pseudo-replication. The honest unit of analysis is the window (n=31), with seeds averaged inside it.
- [STAT] The significance of the headline AS-vs-FS difference depends entirely on that choice. Paired AS−FS mean Sharpe at matched k is +0.077; pooled over all 868 pairs a one-sample t-test gives p=0.024 (Wilcoxon p=0.030), but after averaging the 7 seeds within each window (n=31 per k, the correct unit) the per-k p-values are 0.71 (k=3), 0.41 (k=5), 0.23 (k=10), 0.37 (k=20) — none significant. Reason: the "AS wins" claim is not supported once pseudo-replication is removed. Per-k win rates (38%, 49%, 56%, 54% of pairs) say the same thing.
- [OK] `defence/make_defence_figures.py` already does the window-level paired difference with a bootstrap 95% interval and already decomposes window-spread vs seed-spread. Reason: that is the right analysis — promote those figures into the main results and retire the pooled-std bars in plots/rq1 and plots/rq2.
- [DO] Report a probability-of-improvement / win-rate plus a bootstrap CI on the mean paired difference, not just mean ± std. Reason: this is the current standard in RL evaluation (Agarwal et al. 2021, rliable: stratified bootstrap CIs, interquartile mean, probability of improvement, performance profiles) and is directly applicable with 7 seeds.
- [DO] Prefer interquartile mean or median alongside the mean for Sharpe. Reason: per-window Sharpe std is ~0.9-1.3, i.e. the spread is an order of magnitude larger than the effect, so the mean is outlier-driven.
- [STAT] State the number of configurations tried and deflate or at least caveat the best Sharpe accordingly. Reason: 4 LSTM shapes + 8 RL configs selected against one test set is textbook multiple testing (Bailey & Lopez de Prado's deflated Sharpe; Harvey & Liu on t-stat thresholds in finance).
- [DO] Power statement: with 31 windows and per-window Sharpe sd ~1.0, the minimum detectable paired difference at 80% power is roughly 0.5 Sharpe. Reason: the observed +0.08 is far below that, so the correct conclusion is "no detectable difference", not "AS is better". This framing turns a weak result into a defensible negative result — which the proposal already pre-registered as a valid contribution.
- [OK] 7 seeds per config is above the 3-5 commonly seen and inside a defensible band. Reason: say it, cite Henderson et al. 2018 / Colas et al. 2018 / Patterson et al. 2024 on seed counts and variance reporting, and note that seed spread turned out to be smaller than window spread (the defence figure shows this).

## 6. Retention diagnostic (RQ2's mechanism evidence)

- [BUG] `retention_from_summary` reads `doc["aggregate"]["agent_memory_action_counts_total"]` (retention.py:73-75) but `train.py` never writes an `aggregate` key. Reason: the documented fast path silently returns None for every real run — the diagnostic as shipped does not run on the sweep output.
- [BUG] The plotted retention histogram in plots/rq2/03 sorts `mem_slot_*` columns as text, so mem_slot_10 lands before mem_slot_2 and small-k runs read empty columns. Reason: already identified and fixed in defence/make_defence_figures.py — use the corrected figure and delete or regenerate the broken one so two contradictory figures are not both in the repo.
- [BUG] `concentration()` = 1 − min/max (retention.py:99-111) is a range statistic on counts with no null distribution. Reason: it has no sampling distribution, so "0.6 = strongly skewed" is an assertion, not a result. Use normalised entropy or a chi-square / multinomial test against uniform, and report the value a *random* memory policy produces as the null.
- [DO] The most important missing control in the whole project: AS with uniformly random memory actions, everything else identical. Reason: it is the only way to show that any AS-vs-FS difference comes from *learning* what to keep rather than from AS's different stack composition. One extra sweep arm, same cost as an existing one.
- [BUG] Within a single (k, seed, window) run the memory policy is near-degenerate: the modal slot takes 90% (k=3), 82% (k=5), 74% (k=10) and 63% (k=20) of all overwrites. Pooled across runs the histogram looks mildly non-uniform (max slot share 0.41 / 0.28 / 0.18 / 0.10 vs uniform 0.33 / 0.20 / 0.10 / 0.05). Reason: the pooled figure therefore hides the real finding — individual agents collapse to a nearly *constant* eviction slot, i.e. AS behaves as a fixed (non-FIFO) rule rather than a state-dependent memory policy. That is a genuinely interesting, reportable negative mechanism result, and it is the opposite of what the current pooled histogram suggests.
- [BUG] Retention is measured from `deterministic=True` rollouts (train.py:81). Reason: argmax over the memory head guarantees low-entropy slot choice, so the observed concentration is partly an artefact of evaluation mode. Report stochastic-policy retention too, or measure dependence between observation and memory action (e.g. mutual information / a logistic fit) rather than marginal counts.
- [GAP] Objective 7 of the proposal — "do retentions cluster around identifiable market events (VIX spikes, regime transitions)?" — is not implemented anywhere. Reason: this is the only analysis that directly tests the κ ≪ k* sparsity premise, which the proposal names as the project's central assumption. steps.csv has date, memory_action and position per day, so an event-alignment plot (overwrite behaviour vs VIX percentile / high-vol regime indicator) is a few lines of pandas.
- [GAP] No measure of the effective memory horizon — the age in days of the oldest surviving slot. Reason: this is the cleanest single quantity for "does the agent keep old information", and it is the natural quantitative form of the κ ≪ k* claim. It needs a short replay of the saved policy, not a retrain.

## 7. RQ1 fairness (the LSTM baseline)

- [BUG] Off-by-one information set: in `rollout_lstm` the forecast for test day 0 is made from the window ending on the last *train* day, so each forecast predicts `ret[t]` from observations up to `t-1`, while the PPO agent at day t sees `obs[t]` and earns `ret[t]` (train_lstm.py:77-99 vs timeseries_env.py:52-63). Reason: the LSTM is systematically one day behind the RL agents. RQ1 is "does RL beat a *strong* supervised baseline", so a one-day information handicap undermines the comparison — and the measured gap is large (LSTM 0.082 vs FS 0.387 mean Sharpe), which makes the handicap worth ruling out before the claim is made.
- [BUG] With `threshold: 0.0`, `predictions_to_postsions` can never output flat (lstm.py:97-104): >0 → long, <0 → short. Confirmed in the data — `pos_flat` is exactly 0 in all 868 LSTM rows, while RL agents go flat on 18-34 days per window. Reason: the baseline is forced into a 2-action space while the agents have 3, which is an uncontrolled difference. Sweep a dead-band threshold (e.g. 0, 0.25σ, 0.5σ of the forecast) and report the best.
- [STAT] The LSTM minimises MSE on raw log-returns (std 0.011, mean 0.0003) with no target scaling. Reason: near-zero-variance targets give tiny gradients and push the forecaster toward a constant, which is consistent with the observed near-coin-flip Sharpe. Either standardise the target or report directional accuracy / IC alongside MSE so the reader can see whether the baseline learned anything at all.
- [GAP] No validation-based early stopping for the LSTM: 15 epochs fixed, and hp_id selected on test Sharpe. Reason: same in-sample-selection problem as §4, and a baseline whose capacity was never tuned on held-out data is not a "strong" baseline in the sense RQ1 needs.
- [GAP] No forecast-quality metrics at all: no MSE/MAE, no directional accuracy, no information coefficient, no comparison against a naive (always-long, or lagged-return) forecaster. Reason: if the LSTM is a bad forecaster the RQ1 result says nothing about paradigms; forecast metrics separate "RL framing wins" from "my baseline was weak".
- [DO] Documentation mismatch: train_lstm.py's docstring claims obs *and targets* are z-scored, but only obs are (train_lstm.py:296-303). Reason: small, but it is exactly the kind of claim a marker will check against the code.

## 10. Code quality / reproducibility

- [GAP] `tests/` contains only `__init__.py` — no unit tests. Reason: the correctness of this project rests almost entirely on index alignment (the `shift(-1)` target, the FrameStack/AdaptiveStack cold start, the LSTM window-to-target offset), which is precisely the class of bug that produces plausible-looking wrong results. Three small tests — (a) reward at day t equals position x next-day return, (b) FS and AS reset to identical observations, (c) LSTM forecast index aligns with the day it trades — would catch the two off-by-one issues above and are directly defensible as rigour.
- [BUG] `adaptive_stack.py`'s `__main__` smoke test imports `TimeSeriesEnv`, but the class is named `TimeSeries` (adaptive_stack.py:189 vs timeseries_env.py:5). Reason: the documented self-check cannot run; also a sign the two modules drifted apart.
- [DO] Pin dependency versions in requirements.txt and record the Python version. Reason: SB3/Gymnasium APIs move; without pins the sweeps are not re-runnable, and reproducibility is cheap marks.
- [DO] Record a git commit hash (and the config) in each summary.json. Reason: `config` is saved but not the code version, so a result cannot be tied to the code that produced it.
- [OK] Resume-safe CSV appending, atomic summary.json write, schema check on resume, seeded PPO. Reason: good engineering given the cluster's interruption history noted in research_log.md — but see §1: the resume logic is exactly what corrupted the summary.json aggregates, so fix the aggregation, keep the resume.
- [DO] Note the known env quirks in the limitations section: `terminated` is computed after incrementing `t`, so the final day's observation is a zero placeholder, and the last row's reward uses the final available next-day return. Reason: harmless but visible in steps.csv, and better named by you than found by a marker.
